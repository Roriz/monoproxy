# EnrichReader page translations

The Hugo site keeps flat English-to-Portuguese dictionaries in `src/enrichreader.com/data/translations/`. `shared.json` covers shared templates and common generated interface text. Each page dictionary is named for its route slug (`home.json` for `/`, `enterprise.json` for `/enterprise/`, and so on). A JSON object maps an English source string to its Brazilian Portuguese translation. Keys can contain named placeholders such as `{count}` for generated labels; matching is anchored to the full normalized text so prose and names are not rewritten by partial matches.

Dictionary lookup collapses repeated whitespace and trims the edges. Text keys describe one DOM text node at a time, including punctuation; strings split by inline markup must be translated as separate text nodes. Attributes use the same key space for `title`, `aria-label`, `placeholder`, and `alt`. Metadata `content` values are translated for description, title, Open Graph title/description, and Twitter title/description tags. The document title is handled as a text node. The runtime resolves unique Portuguese values back to English and retains captured placeholder values while switching languages.

Generated web-guide dictionaries translate interface labels and controls. Book-derived names, summaries, facts, quotations, and other story data remain in English; do not machine-translate that content as part of the UI pass. Mark authored English text with `lang="en"`, and keep translatable source labels outside that protected text span. A Portuguese value may write `{article} {position}` where the English key has only `{position}` (for example `Já terminei {article} {position}` for `I’ve finished {position}`); the runtime fills the article from the position (`a` for Carta/Letter, `o` otherwise), so position labels such as `L1 · Carta 1` or `Parte 2 · cap. 3` need their own label keys rather than one sentence per label.

Do not add keys for code, scripts, styles, URLs, data values, or proper names. The runtime preserves the DOM and its event listeners, watches dynamic UI, and can resolve a unique Portuguese dictionary value back to English. Duplicate Portuguese values are skipped for reverse lookup.

Hugo embeds both dictionaries and the runtime in the head before the body is parsed. Standalone pages served by the web-guide Node app use the same approach: define `window.EnrichReaderTranslations = { shared: ..., page: ... }` and inline the runtime synchronously before the body or generated UI is parsed. Provide the same dictionaries to standalone routes; the language selector uses buttons with `data-language-choice="en"` and `data-language-choice="pt-BR"`.

Scripts can localize generated UI through `window.EnrichReaderI18n.t('Show all {count} race selections', { count: 68 })`. The API's `language` property is `en` or `pt-BR`. Manual selector changes dispatch `languagechange` on `document` with `event.detail.language`, allowing already-rendered controls to refresh.

The initial language precedence is `?lang=en|pt|pt-BR`, saved `localStorage` choice, then the first supported English or Portuguese browser language in `navigator.languages`; unsupported browser languages fall back to English. A valid query choice and a manual selector choice are saved under `enrichreader-language`. Manual selection removes a `lang` query override so the saved choice takes effect on the next visit. Storage and URL API failures are handled without breaking the page.

## Crawlable Portuguese pages (/pt-br/)

Crawlers and AI fetchers do not run the runtime, so the reader pages listed in `ptBRPages` in `src/enrichreader.com/hugo.toml` also get a static Brazilian Portuguese copy at `/pt-br/<path>`. Hugo builds the English page with `hreflang` alternates (`en`, `pt-BR`, `x-default` → English), an `og:locale:alternate`, and a header language switch made of links (`<a hreflang data-language-choice>`) instead of buttons. The sitemap lists both URLs with `xhtml:link` alternates.

After Hugo, `bin/build` runs `scripts/web-guide/build-pt-br.mjs`. It finds every built page that declares a `pt-BR` alternate and writes the copy with `src/enrichreader.com/lib/pt-br-pages.mjs`: text nodes, the translatable attributes and the metadata tags are translated by `static/i18n.js` itself (loaded with a stub DOM and called through `EnrichReaderI18n.translateValue`) with the page's own inline dictionaries, under the runtime's exclusion rules. So the copy says exactly what switching the English page in the browser shows, and the dictionaries stay the single source. The copy also gets `lang="pt-BR"`, its own canonical and `og:url`, `og:locale` `pt_BR`, internal links to other pages with a copy rewritten to their `/pt-br/` URL, and a JSON-LD page node with its own `@id`/`url`, `inLanguage: pt-BR`, translated name, description and breadcrumb, and FAQ questions read from the translated FAQ section. Site-wide entities (organization, website, app) are left as they are. Previous copies are deleted first, so removing a page from `ptBRPages` unpublishes its copy.

A missing dictionary key leaves English on the static page exactly as it does in the browser; review new pages with the browser switch or with the `untranslated` callback of `localizePage`. To add a page, give it complete dictionary coverage, then add its path to `ptBRPages`.

On a page with a copy, the URL decides the language. The runtime reads the alternates above it in the head: the English page forwards a saved or browser Portuguese preference (or `?lang=pt`) to the `/pt-br/` URL, keeping the query and fragment; the Portuguese page only moves on an explicit `?lang=en`, never on browser settings, so crawlers with English settings index it as served. Choosing a language in the switch saves it and opens the other version; when storage is unavailable an English choice travels as `?lang=en` so the English page does not send the reader straight back. Other pages keep the in-place translation described above.
